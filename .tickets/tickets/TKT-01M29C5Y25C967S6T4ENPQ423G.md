## Description

Rebuild every projection table from the thread logs. This is the designated recovery path for a lost or corrupted database: users and permissions come back from a database backup, content never does.

The claim in docs/00 that "recovery is ketju reindex" is either true or it is marketing, and this ticket is where it becomes true. Test it by deleting the projection tables of a populated instance and rebuilding.

## Acceptance criteria

- [ ] Dropping every projection table and running reindex restores rows identical to the incremental path
- [ ] Progress is reported for a long run rather than sitting silent
- [ ] The command is safe to run against a live data directory, or refuses to run and says why
- [ ] The README recovery procedure is written from this command and tested end to end

## Implementation plan

Revised at claim (2026-09-28) against main 29566a7.

### Approach
1. `internal/events/projection/reindex.go`: `Writer.Reindex(ctx, progress)` owns the rebuild, because the writer already has the walker, `ProjectThread` and the header check. It walks `threads/` first (so a walk failure changes nothing), empties every projection table with `db.ClearProjections` in one Write, then projects each log from offset 64 to its size, one transaction per thread, in id order. It writes only the database: logs are opened read-only, as everywhere in this package.
   - A log of exactly 64 bytes is unfinished and has nothing to project (as catch-up reports it). A log shorter than 64 bytes is a failure.
   - A thread whose projection fails is looked at again read-only with `threadlog.Open` (full replay, no index). If the only problem is a torn final frame, it is projected to the last whole frame and reported as torn; serve truncates the tail at its next open and its catch-up then finds no gap. Anything else is a failure, reported, and the run goes on to the next thread.
2. `cmd/ketju/reindex.go`: `ketju reindex [--root DIR] [--projections] [--search] [--json]`, the docs/03 signature. `--projections` is the default and the only mode; `--search` is a usage error until TKT-01M29CRJ3B. Order: parse; refuse a root with no `threads/` (usage, like fsck); take the data-directory lock as "reindex" and refuse with the holder named plus "stop ketju serve, then run reindex" if held; create `db/` and open, migrate; reindex; report.
3. Progress (AC2): one line on stderr at the start (threads and bytes to replay), then at most one every 2 s: done/total threads, bytes, rate, time left. The summary goes to stdout, text or `--json`, so JSON output stays parseable. The interval and clock are seams for the test.
4. Exit codes follow fsck/admin: 0 clean (torn tails included), 1 a thread's log could not be projected (damage; fsck names it), 2 usage, 4 the directory is locked or the database could not be opened or written.
5. The database may have no members when the run ends (a lost database, no backup). Reindex says so in a warning, because new sign-ups would be handed the member ids old posts carry. It does not refuse: what to do without a backup is a product decision and is filed as a draft.
6. README "Recovering a lost or damaged database": stop serve; move `db/` aside; copy the backup in; `ketju reindex`; `ketju fsck`; start serve. Says plainly that content comes from the logs, members and permissions only from the backup.

### Tests
- AC1 `TestReindexEqualsIncremental`: many threads with every known record type, projected incrementally through a real bus and writer, then (a) projection tables emptied, (b) projection rows scribbled with stale values, (c) the database files deleted outright; after `reindex` each dump equals the incremental one, and in (a)/(b) authoritative rows survive. A test also fails when a new record type is added that the generator does not write.
- AC2 `TestReindexReportsProgress`: a small interval, many threads; progress lines plus the summary.
- AC3 `TestReindexRefusesWhileLocked`: the test holds the lock as serve; reindex exits 4 naming the holder and serve, and the dump is unchanged.
- AC4 `TestREADMERecoveryProcedure`: extracts the README section's `sh` block and runs it with `sh -eu` against a populated data directory whose database was lost, with a `VACUUM INTO` backup; `ketju` on PATH is this test binary re-executed as main. Afterwards members come from the backup, projections equal the incremental dump, and a catch-up finds no gap.
- Torn tail, damaged log, header-only log, `--search`, missing threads dir.
