## Description

Rebuild every projection table from the thread logs. This is the designated recovery path for a lost or corrupted database: users and permissions come back from a database backup, content never does.

The claim in docs/00 that "recovery is ketju reindex" is either true or it is marketing, and this ticket is where it becomes true. Test it by deleting the projection tables of a populated instance and rebuilding.

## Acceptance criteria

- [ ] Dropping every projection table and running reindex restores rows identical to the incremental path
- [ ] Progress is reported for a long run rather than sitting silent
- [ ] The command is safe to run against a live data directory, or refuses to run and says why
- [ ] The README recovery procedure is written from this command and tested end to end

## Implementation plan

Pre-groom plan (2026-09-24). Revise at claim, after reading the code as it stands then.

### Approach
1. Add `cmd/ketju/reindex.go` with `ketju reindex [--root DIR] [--projections] [--search]`, the docs/03 signature. `--projections` is the default, and the only mode implemented here. `--search` answers an `errUsage` saying search indexing arrives with TKT-01M29CRJ3B, until that ticket extends it. Follow `fsck.go`'s shape: a `reindexMain(w io.Writer, args []string) error` for tests, a flag.FlagSet, and the existing `exit.go` codes.
2. Safety against a live directory: take the data-directory lock from CCBZN before touching anything. If `serve` holds it, refuse with the lock's holder message plus "stop ketju serve, then run reindex". The lock also stops a `serve` from starting mid-reindex. This is the "refuses to run and says why" branch of AC3.
3. Open the DB (`db.Open`) and run `db.Migrate`. A lost database comes back as an empty schema, and the authoritative tables stay empty until a backup is restored. In one write transaction, `DELETE FROM` every table in `db.ProjectionTables` (from BYYJ8). Then walk `threads/` with the same walker as C5Y1S, and call `projection.Writer.ProjectThread(ctx, id, size)` for each log from offset 64. Each thread commits on its own.
4. Crash midway: projection rows exist only for finished threads, and `projection_state` is absent for the rest. A rerun starts over from the DELETE, which is simple and correct. `serve`'s catch-up would also finish the job, because a missing row means replay from 64.
5. Progress: count threads first (a stat-only walk), then log a line every 2 s or every 1000 threads, whichever comes first: done/total, bytes, rate, ETA. Print a final summary. The text goes to w, and `--json` gives a summary object, the same as fsck.
6. README: add a "Recovering a lost or damaged database" section. Stop serve. Restore `db/ketju.db` from the latest backup if there is one; users and permissions come only from there. Run `ketju reindex`. Run `ketju fsck`. Start serve. Say plainly that content never comes from the DB backup.

### Files and packages
New: `cmd/ketju/reindex.go` and `cmd/ketju/reindex_test.go`. Touched: `cmd/ketju/main.go` (usage and dispatch), `README.md` (the recovery section), and the docs/03 "Durability and recovery" bullet if the flag semantics change. Reused: `lock.Acquire` (CCBZN), `db.Open` and `Migrate`, `db.ProjectionTables`, `projection.Writer.ProjectThread`, the C5Y1S walker, `dbtest.DumpProjections`, and `threadcache` in tests to write real logs.

### Tests
- AC1: `TestReindexEqualsIncremental` populates an instance with threadcache appends of every record type, published through a real bus and projection writer. It dumps, drops every projection table (DROP, then migrate recreates them), runs `reindexMain`, dumps again, and asserts the dumps are equal. A second variant deletes `ketju.db` entirely. This test also closes BYYJ8's AC3.
- AC2: `TestReindexReportsProgress` uses a fake clock or a small interval option, and asserts at least one progress line plus the summary for a many-thread fixture.
- AC3: `TestReindexRefusesWhileLocked` has the test hold the CCBZN lock. The command exits non-zero with the holder named, and the DB is untouched (same dump).
- AC4: `TestREADMERecoveryProcedure` is a script-shaped test that runs the README's commands in order against a temp data dir: build the binary with `go build`, then exec. It checks that the README section exists and names each command it runs, so the document and the test cannot drift apart.
