## Description

On start, compare each thread's `projection_state.log_length` against the real log and replay the gap. A crash between a log write and a database write leaves exactly this gap, and closing it on startup is what makes the asynchronous projection safe.

The scan has to stay cheap with ten thousand threads on disk. Reading an index header is 32 bytes and a `stat()` is free, so this is a directory walk rather than a full open of every thread.

## Acceptance criteria

- [ ] A thread whose log is shorter than its projection_state is reported as corruption rather than silently accepted
- [ ] Catch-up is idempotent if the process dies partway through it
- [ ] A gap between projection_state and the log is closed before the listener accepts requests (the server does not serve while catching up, decided in grooming 2026-09-24), and the catch-up logs how many threads it closed and how long it took
- [ ] Catch-up over ten thousand threads with no drift completes in under 2 s on the CI runner without opening every log, enforced by a test or benchmark that fails above that bound

## Notes

**agent:claude/phase1-groom** at 2026-09-24T05:06:25Z

Acceptance criteria rewritten during Phase 1 grooming (2026-09-24), agreed with the user as part of preparing the autonomous run. Rewritten criteria move to the end of the list, so their numbers changed. The first criterion left open whether the server waits for catch-up or serves while catching up. It now waits: at friend-group scale catch-up is short, and 'never serve a stale projection' is the simpler guarantee to test. The rejected alternative, serving with a lag report, needs every read path to tolerate a projection that is behind. 'Bounded time' became a number: under 2 s for 10k threads on the CI runner.
