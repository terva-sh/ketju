# ketju v1.0 — release checklist

This is the checklist the maintainer works through before tagging v1.0. The
Phase 4 exit check (TKT-01M3YMG0NX) wrote it from `main` as it stood when
that ticket merged. The release notes are [v1.0.md](v1.0.md).

docs/09 gives Phase 4's exit criterion as "v1.0 tag". The tag, the secrets
and publishing are outside the repository (docs/15, stop class 3), so the
autonomous run did none of them. Part 1 is the evidence that the work behind
the tag is done. Part 2 lists what the maintainer should settle before
tagging. Part 3 is the maintainer's steps, and part 4 what follows the tag.

Each list in part 2 names the command that finds it, so the list can be
rerun after later merges. Each command runs from a checkout with
`origin/main` fetched. `ed82f15e` is the commit at which Phase 4's grooming
began.

### The advisory move records on rollback

docs/03 "Reserved record type numbers" puts `PostsSplitOut` (20) and
`PostsMergedIn` (21) in the advisory class, because skipping one leaves "a
stale render, not a disclosure". That holds for every released build,
because v1.0 is the first to write or read them.

A build from before Phase 4 that read a v1.0 log would skip them. It would
then show a cross-forum split's posts in the source thread to readers of the
source forum, which docs/15's move rule forbids. A migrated database refuses
an older binary (`TestNewerSchemaRefused`), so the exposure is narrow: only an
older binary's `ketju reindex` over logs that v1.0 wrote.

**Do not downgrade past v1.0 with logs that hold a move.** The record
classes are frozen, so this is a known limit, not something to change.

## 3. What the maintainer does

Each step is outside the repository (docs/15, stop class 3). The run does
none of them.

1. Settle part 2: approve, revert or file each item.
2. Finish the release notes, [v1.0.md](v1.0.md), including its "Decisions
   pending maintainer review".
3. Create the four secrets `.forgejo/workflows/release.yml` reads, as
   secrets of `terva-sh/ketju` or of the `terva-sh` organization. README
   "Publishing a release" says what each one is:
   - `RELEASE_FORGEJO_TOKEN`
   - `RELEASE_GITHUB_TOKEN`
   - `CONTAINER_PUSH_REPO_USER`
   - `CONTAINER_PUSH_REPO_PASSWORD`
4. Push a pre-release tag on `main`'s head, such as `v1.0.0-rc.1`, to the
   GitHub mirror and then here, as README "Publishing a release" says. Then
   check:
   1. The release run's log shows `tools/release`'s assertions, the two
      uploads and the image push.
   2. On a clean machine, the downloaded artifacts pass
      `sha256sum -c SHA256SUMS`.
   3. The image, run with an empty volume and a minimal config, answers
      `/healthz`, and runs as uid 65532.

   These are TKT-01M3YSVEDJ's criteria 1, 2 and 5. Record the result there.
5. Push the v1.0 tag on the commit the pre-release was built from, or on a
   newer `main` after a fresh pre-release. The name is the maintainer's:
   `v*` matches `v1.0` and `v1.0.0` alike, but Go's module tooling reads
   only the three-part form as a version.

The run then ticks TKT-01M3YSVEDJ's three criteria from the maintainer's
