# ketju v1.0.0 — release notes

The first release. The workflow that publishes it
(`.forgejo/workflows/release.yml`; README "Publishing a release") uses this
file as the release's description. The [v1.0 checklist](v1.0-checklist.md)
(TKT-01M3YMG0NX) holds the evidence behind each Phase 4 exit criterion and
the decisions the maintainer settled before the tag.

## What v1.0 holds

ketju is a message board for a small community: one static Go binary,
holding the server, the client and the offline tools, and one data
directory. By roadmap phase (docs/09):

- **Phase 1, the walking skeleton.** Sign-in with OpenID Connect, forums,
  linear threads with pages, the composer with preview, quote and reply,
  edits and soft deletes, read positions, and both the phone and desktop
  layouts.
- **Phase 2, approval and moderation.** Registration by application, with
  forms and a moderator queue; several providers and account linking; lock,
  pin, rename, move, flags, suspension and the audit log; the admin
  screens; agent accounts with bearer credentials.
- **Phase 3, reading.** Lenses (unread, author, reply chain, since,
  mentions, moderator), the cross-forum lists, watches and notifications,
  full-text search, live updates, drafts, attachments with thumbnails, and
  a home-screen web app.
- **Phase 4, polish.** Split and merge, reply as a new thread, slow mode,
  archived threads, thread tags, and quotes recorded as backlinks. Members
  edit their display name, bio and avatar, change their handle, deactivate
  their own account, and may turn the single-key shortcuts off; `/` opens
  search on desktop. What one member may upload and leave unattached is
  bounded. For operators: the metrics endpoint, `ketju backup`,
  `ketju config check` and `ketju version`.

## Platforms

Each release is a static binary for **linux/amd64** and **linux/arm64**,
built with `CGO_ENABLED=0` and `-trimpath`, with a `SHA256SUMS` file beside
them. The binary needs no C library, so it runs on glibc and musl systems
alike. `ketju version` prints the version, the commit it was built from,
the Go version and the platform.

The release is on this forge's release page and on the GitHub mirror's.
The same binaries are in an image, `container.local.sothr.com/terva-sh/ketju`,
tagged `v1.0.0` and `latest`: scratch, CA certificates, uid 65532, a `/data`
volume (README "The container image"). v1.0 is not signed; `SHA256SUMS` is
the check.

Other platforms are not offered (docs/02, after "Backups"): macOS and
FreeBSD because no CI runner starts them, Windows because `serve` needs the
unix data-directory lock, and 32-bit ARM because no runner tests it.

## Upgrading

The README's "Upgrading" section is the procedure: read these notes, take a
backup with `ketju backup`, stop `serve`, replace the binary, run
`ketju config check`, start `serve`, which applies the migrations, and run
`ketju fsck`. Going back means the old binary and the backup together,
because an older binary refuses a database a newer one has migrated.

The procedure runs as a test (`TestREADMEUpgradeProcedure`) against a data
directory the build at ed82f15e wrote, so an upgrade from any Phase 3 or
later build is covered.

The first start of v1.0 replays every thread log once, from its first
record, to record which posts quote which (migrations 0025 and 0030, quote
backlinks). A log shorter than the database recorded is still quarantined
first, as on any start, and is not replayed. Pages are served once it has
caught up; on a large forum the first start takes longer than usual.

Do not go back past v1.0 once a moderator has split or merged posts. A
binary older than v1.0 skips the two move records, so its `ketju reindex`
would show moved posts in their old thread again. Going back means the
backup taken before the upgrade (README "Upgrading").

## Known limits

- **JavaScript is required.** The client is a single-page app. The HTML
  client that works without JavaScript is Phase 5, after v1.0.
- **One process.** `serve` holds the data directory's lock, and the thread
  logs and the database are written by that one process. Scale is a small
  community on one machine.
- **No TLS of its own.** Run `serve` behind a reverse proxy that terminates
  TLS, and set `site_url` to the address people use.
- **No signatures.** v1.0 publishes `SHA256SUMS`, unsigned, by the
  maintainer's decision. The sums prove a download whole, not who built it.

## Decisions the runs made

The design documents mark each decision the autonomous runs made without
the maintainer as "Decided by the run". The maintainer approved every one
still open on 2026-10-03, the platform list above among them, and each now
reads "maintainer approved". One stands for v1.0 only: a signed-out reader
is still sent each author's avatar hash, which fetches nothing
(TKT-01M41MKE81 removes it).
