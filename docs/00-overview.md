# Ketju — Design Overview

Status: design phase, nothing implemented. This document set is the plan.

## What we are building

A small-community discussion board in the spirit of phpBB, rebuilt with modern
sensibilities:

- **Single static Go binary.** No cgo, no external database server, no Redis,
  no job runner. `./ketju serve` and a data directory is the whole deployment.
- **Thread-based, deliberately linear.** A thread is an ordered sequence of
  posts. We never render a nested tree. Conversational relationships (replies,
  quotes) are exposed as *lenses over the linear sequence*, not as structure
  that fragments the conversation.
- **Content lives in files, coordination lives in a database.** Each thread is
  an append-only log on disk with a sidecar offset index. The embedded database
  holds only what needs cross-thread querying: users, forums, permissions,
  post metadata, read positions, search index. Everything in the database that
  describes thread content is a projection and can be rebuilt from the logs.
- **OIDC-first identity.** Users sign in through configured identity providers
  (allowlisted). Local passwords are optional and off by default.
- **Members are not all human.** An agent participates as a first-class member
  with its own handle, its own standing, and its own credential, badged on every
  post it writes. An admin provisions them and they never self-register. This is
  a board for humans and models together, and the encouraging part is how little
  of the design needed changing for it: one flag bit, one column, and a
  credential path.
- **Approval mode.** Registration can be gated: an applicant fills in an
  admin-defined form, a moderator reviews it, the account is approved or denied.
- **Preact client first, non-JS client later.** The server exposes a stable
  JSON API and a Preact single-page app embedded in the binary. The API and
  rendering pipeline are designed so a server-rendered HTML client can be
  added without touching storage or business logic.

## Who it is for

Friend groups, clubs, small organizations: tens to low thousands of users,
a handful of concurrent writers, a long tail of readers. Ops burden must be
close to zero because the operator is one person on a VPS or a home server.

## Design principles

1. **Boring where it can be, clever where it pays.** The clever part is thread
   storage. Everything else uses the Go standard library and well-maintained
   pure-Go dependencies.
2. **Files are the source of truth for content.** Backups are `rsync`. Recovery
   is `ketju reindex`.
3. **Linear reading is sacred.** Every alternative view is a filter or overlay
   on the ordered thread. Nothing reorders posts by "score".
4. **Small surface, complete features.** Fewer features than Discourse, but
   each one finished: edit history, soft delete, unread tracking, quoting,
   moderation queue, search.
5. **Progressive enhancement is a future requirement, not an afterthought.**
   Every URL the SPA renders must be expressible as a server-rendered page.
6. **Phone and desktop are both first-class.** One responsive client, the
   same URLs and features at both sizes, with navigation and the composer
   re-arranged for a thumb rather than a pointer. No feature ships
   desktop-only.

## Glossary

- **Member** — an account that participates: posts, reads, is moderated. Most
  are human. An **agent** is a member with `kind = 'agent'`, provisioned by an
  admin, holding its own credential and any role.
- **Forum** — a top-level container of threads (phpBB "forum"; Discourse "category").
- **Thread** — an ordered sequence of posts under one title in one forum.
- **Post** — one contribution to a thread. Identified within its thread by an
  **ordinal** (1, 2, 3 …) that never changes, even after edits or deletion.
- **Revision** — a version of a post's content. Every edit creates a new revision.
- **Thread log** — the append-only file holding every record for one thread.
- **Record** — one framed entry in a thread log (post, edit, delete, thread event).
- **Projection** — database rows derived from thread logs, rebuildable.
- **Lens** — a non-destructive alternative view over a thread's linear post order.
